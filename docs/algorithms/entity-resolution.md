# Cross-session entity resolution

Owner: Pipeline. Code: `src/medmemgraph/pipeline/resolve.py` (uses
`src/medmemgraph/pipeline/ids.py`, unmodified — see "Files to touch" note
below). Tests: `tests/test_resolve.py` (34 tests, offline, LLM stubbed).
Fixture: `fixtures/er/alias_metformin.json`. Eyeball artifact:
`samples/resolve-eyeball-<subject_id>.md` (generated by
`scripts/generate_resolve_eyeball.py`).

This document explains the four algorithmically load-bearing decisions in
`resolve.py` — a reviewer checking this story against `ARCHITECTURE.md`
§6.3/§5.4, `collaborative/design/stories/E3/E3-S1.md`, and
`collaborative/literature/04-entity-resolution-and-ontology.md` ("survey
04") would otherwise have to reconstruct them from the code: (1) why
blocking is lexical-only rather than embedding-based, and what that
genuinely costs; (2) the representative-anchored transitivity guard and the
real bug the corpus run found in its size cap; (3) the two-phase incremental
design that keeps ids stable across admissions; (4) what the real-corpus run
actually proved and did not prove.

## 1. The pipeline, in one picture

```
ClinicalFacts (subject/object EntityRefs, canonical_id=0 placeholder)
    -> Mention (one per non-Patient EntityRef, Patient refs minted directly)
    -> block(mentions)                     cheap candidate generation
    -> per block: match existing anchors,  incremental — see §3
       then representative-anchored
       clustering of what's left           the transitivity guard — see §2
    -> CanonicalEntity per cluster          canonical_name + aliases[] + mentions[]
    -> ids.mint_entity_id(patient, type,
       canonical_name)                      §5.4's mint, never reminted downstream
    -> attach_canonical_ids rewrites every
       fact's subject/object.canonical_id
       in place
```

`:Patient` refs never go through ER at all — patient identity is exact by
`subject_id`, minted directly via `ids.mint_patient_id`. Only domain-entity
refs (`Medication`, `Condition`, `Symptom`, `Procedure`, `Allergen`, ...)
are fuzzy-resolved.

One canonical node per entity, aliases folded into a **list** property
(`CanonicalEntity.aliases`), never `SAME_AS` alias nodes
(`tests/test_resolve.py::TestNoSameAsRelationshipType` greps the whole
source tree for this). `ARCHITECTURE.md` §5.2 and survey 04 Q3 both name
the reason: an alias-node-plus-`SAME_AS` model forces every downstream
traversal to first collapse through those edges, which is expensive in an
engine with a 16-hop ceiling and no `IN`. `resolve.py` decides merges; the
Graph writer decides how `aliases` gets serialized onto the domain node
(a delimited string, per `E3-S1.md`'s Boundary note — HydraDB has no list
functions) — that serialization is explicitly not this module's job.

## 2. Blocking is lexical-only — a stated trade, and what it actually costs

`ARCHITECTURE.md` §6.3 point 2 and `E3-S1.md`'s algorithmic contract both
specify a **two-signal** blocking scheme: an exact normalized key, plus
embedding-cosine kNN over "name + one-turn context" for the paraphrase case.
This module implements only the first signal (`block()`: exact normalized
key, token-Jaccard, character-trigram Dice) plus one small, bounded,
non-ML addition (`_KNOWN_ALIAS_GROUPS`, described below) — no embedding
call.

This is a stated, argued trade, not an oversight, and it is the same trade
`normalize.py` already made for predicate canonicalization (EDC
embed+LLM-confirm traded for a pure alias table, documented in that
module's own docstring). The reason is structural, not a preference: this
repo has no embedding dependency in `pyproject.toml`, no embedding client
configured, and no `ANTHROPIC_API_KEY` in this sandbox (checked directly,
same finding every prior `[dev-ml]` log entry has made); Anthropic itself
does not expose an embeddings endpoint (checked the `claude-api` skill
directly — zero hits for "embed" — rather than assumed from training-data
memory, per this repo's own trigger rule for Anthropic-API code). Adding a
real embedding backend (Voyage/OpenAI-class) would be a new dependency
outside this story's scope — a HALT trigger under this project's hard
rules, not a same-story implementation choice.

**What this honestly costs**, stated plainly rather than glossed over: pure
lexical similarity is a linguistic dead end for the story's own headline
example. "Glucophage" and "metformin" share zero substrings; "my diabetes
pill" and "metformin" share zero substrings. No token-Jaccard or
character-trigram metric — however tuned — can bridge a brand/generic pair
or an open colloquial description, because bridging them requires knowing
what the words *mean*, not how they're spelled. `block()` and `resolve()`
both thread an optional `embed` callable point through their design even
though nothing calls it today, specifically so a real embedding backend
can be wired in later without changing this module's contract.

As a small, explicitly-scoped stand-in — not a semantic solution — `block()`
also folds names through `_KNOWN_ALIAS_GROUPS`, a short, hand-reviewable,
zero-parameter gazetteer of well-known US brand↔generic pairs for this
corpus's own documented medication lexicon (same category of artifact as
`normalize.py`'s `_PREDICATE_ALIASES` table). It catches exactly the finite
pairs listed (`glucophage -> metformin`, `lasix -> furosemide`, ...) and
does **not** generalize to open descriptions. `match()` treats a
gazetteer-fold the same as an exact key: a certain, zero-cost merge that
never touches the LLM.

The real-corpus run (§5) demonstrates the honest boundary of this design
directly: dozens of identical mentions of a repeated term collapse onto one
canonical node for free, but the rule-based extraction path used in that
run happens to never produce surface-form diversity in the first place (see
§5) — so the paraphrase-bridging case is validated instead by
`tests/test_resolve.py::TestAliasFixtureEndToEnd`, a synthetic fixture with
a scripted "always match" LLM stub, which shows "metformin" / "Glucophage" /
"METFORMIN." landing on one canonical id while "the 500mg one" — a
colloquial description covered by neither the lexical metrics nor the
gazetteer — is left as its own separate entity. That negative case is
tested and named on purpose (`test_colloquial_description_is_the_
documented_gap_not_a_silent_merge`), not hidden.

## 3. The transitivity guard, and the real bug the corpus run found in it

Naive connected-components clustering over pairwise match edges has a
well-known failure mode (survey 04's own framing, and the story's explicit
instruction to guard against it): if `match(A, B)` is `True` and
`match(B, C)` is `True`, but `match(A, C)` would be `False`, chaining
through `B` incorrectly merges `{A, B, C}`.

`resolve()` never does connected-components. Each block resolves via
**single-pass representative-anchored clustering**: the first unresolved
mention in a block opens a cluster as its fixed representative; every later
candidate is compared only against each open cluster's representative,
never against an arbitrary other member. `C` is only ever asked "are you
the same as `A`?" — never "are you the same as `B`?" — so the chain-through
case cannot occur by construction.
`tests/test_resolve.py::TestTransitivityGuard::
test_representative_anchoring_stops_a_bad_chain_merge` constructs exactly
this scenario (scripted `A-B: True`, `A-C: False`, `B-C: True`-if-asked) and
additionally asserts the `B`–`C` pair is *never even asked* — the strongest
form of the guard, not just the right final answer.

A second, independent cap (`MAX_CLUSTER_SIZE = 12`) bounds runaway growth
even within the representative-anchored scheme. Its exact semantics were
wrong in the first version of this code, and fixing that is the single most
useful thing the real-corpus run did:

> **The bug, found on real data, not by unit tests alone.** The first
> version capped on *total cluster membership*. Run against patient
> `13813803`'s 64 real admissions, the `endoscopy` cluster grows to 36
> members purely via harmless exact-key matches (the same word, mentioned
> 36 times) — past the cap of 12 well before any fuzzy comparison is
> needed. When a genuinely different candidate later needed a *fuzzy*
> comparison against that cluster (`colonoscopy`, coincidentally
> lexically close enough to block alongside it), the total-membership
> cap silently skipped the comparison **without ever calling `match()`**.
> That is exactly the story's own headline under-merge failure mode —
> a frequently-mentioned entity permanently unable to absorb one later
> paraphrase/brand-name candidate — reproduced by the mechanism meant to
> guard against a *different* failure mode, purely because the entity
> happened to be common. Fixed by capping **fuzzy-join count**, not total
> membership: an unbounded run of exact-key joins carries zero
> transitivity risk (it is not an inference chained through a weak link;
> it is the identical string, restated) and must never count against a
> cap whose whole purpose is bounding *unverified* inference chains.
> Regression-locked by
> `tests/test_resolve.py::TestTransitivityGuard::
> test_cap_counts_fuzzy_joins_not_total_membership_regression`, which
> reproduces the exact shape (20+ exact matches, then one legitimate fuzzy
> candidate) and asserts the fuzzy candidate is actually compared, not
> silently dropped.

This is the concrete argument for why the story's "then run it for real"
instruction is not a formality: this exact defect — real, and directly in
the failure direction the story cares most about avoiding — was invisible
to every hand-constructed unit test (which each exercised either pure exact
growth or pure fuzzy growth, never the mixed sequence a real, frequently-
mentioned entity actually produces) and visible on the first real run.

## 4. Incremental resolution — why ids stay stable across admissions

`ids.mint_entity_id(patient_id, entity_type, canonical_name)` hashes on
`normalize_key(canonical_name)`. That means **id stability across
incremental runs depends entirely on never changing which surface form is
chosen as `canonical_name` once an entity exists** — if session 3 chose a
different "first-seen" name than session 1 did for the same real entity,
the minted id would silently change, which is exactly the duplicate-node
failure this whole module exists to prevent.

The design keeps this stable with a `CanonicalRegistry` (`patient_id ->
list[CanonicalEntity]`, JSON-round-trippable) as the incremental seam:

1. Load the registry (or start empty on session 1).
2. Turn every `existing` canonical into a synthetic *pseudo-mention* (its
   current `canonical_name`, never its aliases) and feed it into the same
   `block()` call as the new admission's mentions.
3. Within a block that contains an existing-canonical pseudo-mention, every
   new mention is matched **against that pseudo-mention first**. A match
   appends an alias to the existing `CanonicalEntity` object in place —
   `canonical_name` and `canonical_id` never change.
4. Only mentions that matched no existing canonical proceed to Phase 2
   (the representative-anchored clustering, §3) to potentially form a
   brand-new canonical entity, with a freshly minted id.

`attach_canonical_ids` rewrites facts using **object-identity filtering**
(`id(mention) in this_call's mentions`), not by trusting every mention
inside a returned `CanonicalEntity.mentions` list blindly — a load-bearing
correctness point found while writing the code, not left implicit: an
`existing` canonical's `.mentions` list accumulates across every past call,
so a historical mention's `fact_index` points into a *different* (past)
`facts` list. Blindly trusting it on a second incremental call would
mutate the wrong current fact (or index out of range). Filtering to this
call's own `Mention` objects by Python identity is what makes a second,
later `attach_canonical_ids` call safe.
`tests/test_resolve.py::TestIncrementalResolution::
test_second_admission_does_not_renumber_first_admissions_entities`
verifies this directly: a second admission's facts, resolved against a
registry populated by a first admission, leave the first admission's own
already-assigned ids byte-for-byte unchanged, and a repeat mention of the
same drug resolves onto the *same* id rather than minting a new one.

## 5. The real-corpus run — what it proved, and what it honestly did not

Run: `uv run python scripts/generate_resolve_eyeball.py --subject 13813803`
(64 real admissions, 3522 real turns, no `ANTHROPIC_API_KEY` in this
sandbox). Full numbers and the largest clusters are in
`samples/resolve-eyeball-13813803.md`; summarized here:

| Metric | Value |
|---|---|
| ClinicalFacts extracted | 726 |
| Non-Patient mentions fed into ER | 728 |
| Blocks | 37 |
| Naive pairwise comparisons avoided | 264,628 -> 24,364 |
| **Reduction ratio** | **0.908** |
| Canonical entities | 39 |
| `match()` calls: exact-key / llm_calls / llm_failures | 689 / 0 / 2 |
| Entities with more than one alias | 0 / 39 |

**What this proves, genuinely:** blocking gives a 90.8% reduction in
required comparisons on real data, and repeated mentions of the same term
across up to 64 separate admissions correctly collapse onto one canonical
node each at zero LLM cost (`'nausea'` × 151, `'surgery'` × 72, `'fever'` ×
64 — see the eyeball file) — end-to-end cross-session deduplication works
on the real corpus, not just in a synthetic fixture. It also caught the
real cap bug described in §3, which the synthetic unit tests alone did not.

**What it honestly does not prove:** the paraphrase/alias-bridging case
this story is named for. Every one of the 39 canonical entities in this run
has exactly one alias — not because ER failed to merge anything, but
because `extract.py`'s rule-based fallback (active in this sandbox for the
same no-API-key reason `resolve.py` also degrades) always emits its fixed
lexicon term verbatim (`object_name` is always literally `'surgery'`,
never `'the surgery'` or `'my operation'`), so there is zero surface-form
diversity in this run's *input* for ER to resolve in the first place. The
metformin/Glucophage/"the 500mg one" case requires the LLM extraction path
(which preserves each mention's own wording) to even appear as an input —
that case is validated instead by `tests/test_resolve.py::
TestAliasFixtureEndToEnd`, offline and LLM-stubbed. Re-running this exact
script with `ANTHROPIC_API_KEY` set (LLM extraction + LLM entity matching
both live) is the natural next validation step and is not something this
sandbox can do.

**Where it over- or under-merged, stated plainly (the story's own
instruction):** no over-merge occurred or is possible on a no-LLM run
(`match()` never says yes when it is never asked to adjudicate a fuzzy
pair). Under-merge is real and expected: every candidate that needed a
fuzzy or gazetteer-uncovered comparison stayed separate, by design, in the
conservative direction ARCHITECTURE §6.3 itself specifies ("failed ER
degrades to new entity rather than a wrong merge — wrong merges silently
break invalidation"). Two coincidental lexical near-misses were also
inspected directly (`{'colonoscopy', 'endoscopy'}`,
`{'300mg', '600mg'}` dosage values) — both correctly resolved to no-merge,
and the dosage-value case is flagged forward as a design note: purely
numeric-plus-unit strings are the shape most likely to trigger a
coincidental char-trigram block, harmless today only because a merge still
requires LLM confirmation.

## 6. Reconciling two spec documents (stated, not silently picked)

This story's direct dispatch (the authoritative context for this
implementation, per this project's established precedent for resolving
divergent specs — see the `[dev-ml]` E2/E7-S5 log entries) specifies a
four-function API (`block`, `match`, `resolve`, `attach_canonical_ids`)
built from lexical blocking signals and a **pairwise** `match(a, b)`. The
on-disk `E3-S1.md` / `ARCHITECTURE.md` §6.3 additionally names an
embedding blocking signal (§2, above) and prefers **listwise** LLM
adjudication over pairwise once a block exceeds ~3-4 candidates (survey 04
R-ER-10: ~16 F1 points on average, because listwise selection lets the
model use record-to-record context pairwise comparison structurally
cannot). This implementation follows the direct dispatch's literal
pairwise `match(a, b)` — which is also the transitivity guard's mechanism
(§3) — and does not implement the listwise batching optimization. Cost is
bounded instead the way this project always bounds LLM cost: an
exact-key/gazetteer fast path that never touches the LLM, aggressive
caching by normalized pair key (reusable across a whole `resolve()` call,
and across future incremental runs if the caller persists the cache dict),
and — per the real-corpus run — genuinely few fuzzy comparisons in
practice (2 out of 728 mentions on a 64-admission patient). If a future
story needs to reduce LLM calls further on a block with many genuine
fuzzy-only candidates, batching `match()`'s calls into one listwise prompt
per block is the documented next step, not implemented here.
