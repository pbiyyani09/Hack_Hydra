# Extraction, assertion handling, and temporal normalization

Owner: Pipeline. Code: `src/medmemgraph/pipeline/extract.py`,
`src/medmemgraph/contracts.py`, `src/medmemgraph/pipeline/normalize.py`.
Tests: `tests/test_extract.py`, `tests/test_contracts.py`,
`tests/test_normalize.py`. Eyeball artifact:
`samples/extract-eyeball-<subject_id>.md` (generated by
`scripts/generate_extract_eyeball.py`).

This document explains the algorithmically load-bearing decisions in this
pair of modules — a paper reviewer (or a code reviewer checking this story
against `ARCHITECTURE.md` §6.1/§6.2 and
`collaborative/literature/14-information-extraction-negation-temporal.md`)
would otherwise have to reconstruct them from the code: (1) how the i2b2
six-class assertion taxonomy is folded onto the frozen binary `polarity`
field without widening it, (2) why structured output through a single
provider-agnostic seam rather than prompted JSON or a direct SDK call, (3)
how relative time is resolved against the turn's own clock rather than
wall-clock time, (4) the predicate-canonicalization and
`CURRENT_DOSAGE_OF` design trades (§§4–5), (5) why the rule-based
fallback is now `dry_run`-gated rather than key-presence-gated, and what
that fixes (§6), and (6) the subject/object role-reversal repair — a
silent-corruption bug in `TAKES_MEDICATION` (and occasionally other
patient-subject predicates) that the drop-log view alone could never
surface, and the three-layer fix (§7).

## 1. The handling rules — decision 002 stays open, on purpose

`decisions/002-polarity-field-underspecified.md` is **open**: the frozen
`ClinicalFact.polarity` field is `asserted | negated`, full stop.
`literature/14`'s own survey (Part 3) is the reason this is a live tension
rather than a settled one: the i2b2 2010 taxonomy has six classes —
`present`, `absent`, `possible`, `conditional`, `hypothetical`,
`associated-with-someone-else` — and the two classes a binary field
collapses without care are exactly the two rule-based *and* LLM-based
systems handle worst. `literature/14` R-IE-04 shows a well-tuned rule-based
system reaches F<0.001 on "Possible" detection out of the box; R-IE-28 shows
zero-shot GPT-4o-class models are specifically 23.4 points worse on
Hypothetical and 10.1 points worse on Associated-with-Someone-Else than a
fine-tuned model, even while scoring ~0.90 overall. Those are the two
clinically dangerous failure directions the brief names: *"if the fever
returns, restart it"* must not become a live prescription, and *"family
history of diabetes"* must never attach to the patient.

The design response — implemented identically in both `extract.py`'s LLM
path and its rule-based fallback — is to let the model emit the full
six-class tag as **scratch state** that never reaches the wire:

```
present                       -> emit, polarity = asserted
absent                         -> emit, polarity = negated   (a denial is information)
possible                       -> emit, polarity = asserted, confidence *= 0.5
conditional / hypothetical      -> DO NOT EMIT — skip beats mis-extracting
not-associated-with-patient     -> DO NOT EMIT — never attach to the patient
```

Three things about this table are load-bearing, not incidental:

- **`possible` never becomes a third polarity value.** decisions/002's
  proposal explicitly warns that a `possible` fact must not silently promote
  to full assertion *or* demote to negation — both are documented failure
  directions (`literature/14` R-IE-04). The confidence discount
  (`_POSSIBLE_CONFIDENCE_DISCOUNT = 0.5`, `extract.py`) is the entire
  mechanism decision 002 gets today; the fact is asserted, at half
  confidence, and nothing downstream treats "possible" as its own polarity.
- **The tag itself is logged, not written.** Every handling decision — kept
  or dropped, and why — is appended to `Extractor.assertion_log` as an
  `AssertionLogEntry`. That dataclass is a pure side channel: it is never
  read by `contracts.validate()`, never serialized onto a `ClinicalFact`,
  and has no field on the frozen contract. This is the literal reading of
  decisions/002's own text — *"A side log of i2b2 assertion tags is allowed
  and encouraged, but it must NOT drive writes or closes."*
- **Skipping is a first-class outcome, not an edge case.** `conditional` and
  `hypothetical` facts are dropped before predicate canonicalization or time
  resolution ever runs on them — there is no code path that could turn a
  hypothetical into a stored fact by accident later in the pipeline. The
  eyeball artifact's "Facts deliberately NOT emitted" section exists
  specifically so a human reviewer can check this against real turns, not
  just against the handling-rule table.

## 2. Structured output through the seam, not "respond in JSON"

`extract.py` no longer talks to a provider SDK directly. Every real call is
`llm.complete(prompt, model=llm.EXTRACT_MODEL, schema=_EXTRACTION_SCHEMA,
system=_SYSTEM_PROMPT, ...)` — a single call into `src/medmemgraph/llm.py`,
the one seam `extract.py` / `eval/judge.py` / `eval/reader.py` are all meant
to route every real inference call through (this module is the first of the
three actually rewired onto it). `extract.py` hands the seam a **plain**
JSON Schema dict — no `additionalProperties`/`strict` flags, no
provider-specific shape — and `llm.py` normalizes it per provider itself
(OpenAI strict mode requires `additionalProperties: false` + every property
`required`; Google's public `GEMINI_API` surface rejects
`additionalProperties` outright and only accepts a restricted OpenAPI-3.0-
like `Schema` subset). Hand-adding either provider's flags at this call site
was exactly the kind of thing `llm.py`'s own docstring warns gets forgotten
in one branch mid-bulk-run; the schema below is untouched from before this
rewire for exactly that reason.

This still uses native structured output, not a bare "respond only with
JSON" instruction, for two independent reasons: `literature/14` R-IE-34
(TANL/SPAN-style structured generation formats measurably outperform
BIO-style token tagging for LLM-based clinical NER) and, more generally,
`literature/17` R-GSJ-001/R-GSJ-002 (naive prompted-JSON-mode measurably
degrades output *quality* on non-classification tasks — up to a 63.1-point
accuracy drop on one Claude-3-Haiku benchmark — while schema-constrained
decoding, which is what `llm.py` actually invokes on both providers, does
not carry that penalty). The `_EXTRACTION_SCHEMA` additionally requires an
`evidence_quote` field per candidate fact (a one-field Chain-of-Note:
`ARCHITECTURE.md` §6.1 calls Chain-of-Note "the highest value-per-hour item"
for the extract prompt) so every candidate is grounded in a verbatim quote
from the source turn, both for the model's own benefit while generating and
for the eyeball artifact's "source snippet" column.

**A retry loop this module used to run itself is gone, deliberately.** The
pre-rewire version re-prompted with corrective feedback ("your previous
response did not match the schema") on a parse/shape failure, once, before
giving up. `llm.complete()` now owns that: up to 2 extra round trips on a
schema-validation mismatch, plus its own transient-failure retry/backoff,
all in the one seam. Running a second, drifting copy of that logic here
would be exactly the "three copies of the same plumbing" problem `llm.py`'s
own module docstring names as its reason for existing. This leans on
native schema-constrained decoding actually constraining the provider's own
decoding — unlike the free-text-JSON-then-reparse world the prior
Anthropic-direct implementation ran in, a genuine schema-validation failure
after `llm.py`'s own retries is expected to be the rare case, not the common
one the old corrective-feedback prompt edit was built to recover from.

## 3. Temporal grounding — the turn's own clock, never wall-clock

`ARCHITECTURE.md` §6.2 and `literature/14` Part 4 converge on the same
number: temporal-expression *detection* is easy (~90% span F-score across
two independent benchmarks, i2b2 2012 and TempEval-3/HeidelTime — R-IE-18,
R-IE-19) but *value normalization* is the real bottleneck (~73–78%). Both
source benchmarks land on the same explanation and the same discipline:
absolute dates are easy, relative expressions are hard, and a
high-precision system should snap to the coarsest defensible anchor and
lower its confidence rather than fabricate a specific date it isn't sure
of.

`normalize.resolve_time(expr, turn_time, *, prior_admission_end=None)`
implements that discipline as a pure function — no LLM, no network, no
`datetime.now()` anywhere in the module (`tests/test_normalize.py`'s
`TestResolveTimeNeverAnchorsToWallClock` patches `datetime.now` to the
harness's real wall-clock date specifically to prove this). The anchor is
always `turn_time`, parsed as-is — MedLoCoMo timestamps are MIMIC
date-shifted into the 2100s+, and nothing in this module or in
`extract.py`'s prompt assumes the present era. Confidence is tiered by how
much the module actually knows:

| Tier | Example | Confidence |
|---|---|---|
| Absolute date in text | `"2124-01-05"`, `"January 5, 2124"` | 1.0 |
| No expression at all | `""` | 1.0 (the anchor *is* correct) |
| Exact relative unit | `"14 days ago"`, `"yesterday"` | 0.9–0.95 |
| `"since my last visit"`, resolved | needs `prior_admission_end` | 0.8 |
| `"last <weekday>"` / `"last week"` | | 0.6–0.85 |
| Vague quantity | `"a couple of weeks ago"` | 0.6 (same date as "two weeks ago", lower confidence) |
| Vague duration | `"a while back"`, `"some time ago"` | 0.3 (returns the anchor, does not guess) |
| Unrecognized text | anything else | 0.4 (returns the anchor) |

The `"since my last visit"` case is the one genuinely stateful resolution:
it needs the *prior* admission's end date, which is not visible from a
single turn. `extract.py`'s `Extractor._prior_admission_ends` computes this
once per admission (the immediately preceding entry in
`Conversation.admissions`, which `pipeline/loader.py` already returns in
admission order) and passes it through; when there is no prior admission —
the patient's first on record — `resolve_time` falls through to "return the
anchor, lower confidence" exactly as the vague-duration case does, per the
story's own instruction: *"Return the anchor when unresolvable rather than
guessing, and lower confidence."* This is exercised end-to-end (LLM path,
scripted) in `tests/test_extract.py::TestSixAssertionTagHandlingRules::
test_possible_time_expression_still_resolves_via_normalize`, and confirmed
against the real corpus in the eyeball artifact — subject `10056223`,
admission `26605038`, turn 11: *"I've been on 60 mg of furosemide since my
last visit"* resolves `valid_from` to `2122-07-13T12:09:00`, the prior
admission's own `admission_end`, not the current turn's `2122-08-13
07:33:00`.

## 4. Predicate canonicalization — a deliberate simplification of the on-disk story

The on-disk story `collaborative/design/stories/E2/E2-S2.md` specifies an
EDC-style pipeline (`literature/04`): embed the raw phrase plus a
definition, take the nearest-neighbour closed-vocabulary definition by
cosine similarity, then confirm with one LLM call. This story's contract
(the packet this module was actually built from) trades that for a pure,
deterministic alias/definition lookup — `normalize.canonicalize_predicate`
has no embedding call and no LLM call, and is fully unit-testable without a
key. The trade is stated explicitly, not silently: `PREDICATE_DEFINITIONS`
(the one-line definition per predicate, reused verbatim in `extract.py`'s
system prompt so the prompt's vocabulary description and the canonicalize
pass can never drift apart) is preserved from the on-disk story's own text,
but the matching mechanism underneath it is simpler. Matching is exact-alias
first, then a token-overlap fallback that requires either two overlapping
tokens or one overlapping token that is both non-generic (a
`_STOPWORD_TOKENS` list — `with`, `of`, `on`, `to`, …) and at least four
characters, specifically so a phrase like `"enjoys hiking with"` cannot
canonicalize onto `TAKES_MEDICATION` just because it shares "with" with
`medicated_with`/`diagnosed_with` (`tests/test_normalize.py::
TestCanonicalizePredicateNoneCase` and a fixed regression test guard this).
Nothing outside `canonicalize_predicate`'s own alias table can invent a
predicate string — a phrase that does not match returns `None`, and
`extract.py`'s handling rules drop the candidate fact rather than emitting
an off-vocabulary predicate (`tests/test_extract.py::
TestUncanonicalizablePredicateIsDropped`).

## 5. `CURRENT_DOSAGE_OF`'s subject convention

Six of the seven closed predicates have the patient as `subject` and a
domain entity as `object` — the usual `(:Patient)-[:HAS]->(:Claim)-[:ABOUT]->
domain-entity` shape. `CURRENT_DOSAGE_OF` is the one exception:
`ARCHITECTURE.md` §4's field note reads it literally — *"the current dose of
the named medication is the object"* — which only parses if `subject` is the
medication and `object` is the dose value. §5.2's own relationship-type
table backs this reading: `ABOUT` attaches to "the claim's object (**and**,
when the subject is not the patient, the subject)" — i.e. the schema
explicitly anticipates a non-patient subject and gives it its own `ABOUT`
edge. `extract.py` implements this as the one predicate-conditional branch
in `_handle_candidate`: `subject = EntityRef(name=<medication>, type=
"Medication", ...)` when `predicate == "CURRENT_DOSAGE_OF"`, patient
otherwise. Both the LLM system prompt and the rule-based fallback's dosage
regex follow the same convention (`tests/test_extract.py::
TestCurrentDosageOfSubjectConvention`; the eyeball's rows 10/12 for real
corpus examples — `furosemide -> 60mg`, `spironolactone -> 300mg`).

## 6. The rule-based fallback is a floor, not the deliverable — and it is now opt-in, never an accident

**This section describes a behavioural change, not just an implementation
detail.** Before this rewire, `Extractor.__init__` decided once, silently,
at construction, whether to call the real Anthropic API or fall back to the
rule-based matcher — based purely on whether `ANTHROPIC_API_KEY` happened to
be set. That module also imported `anthropic` directly, which was removed
from this project's dependencies once the `medmemgraph.llm` seam (§2 above)
replaced it as the intended transport for every LLM-dependent module in this
repo. The combination was silent, indefinite degradation: every fact this
module ever emitted — the eyeball artifact, every extraction test's real
run, everything — came from the rule-based floor, and nothing in the code
or its output ever said so *at the point the degrade happened*. The eyeball
artifact's own bold header was the only place this was visible, and only
because a human wrote it in by hand.

The fix changes the trigger from *"is a key configured?"* to *"did the
caller explicitly ask for the stub?"*:

- `Extractor(dry_run=True)` (or `$MEDMEMGRAPH_EXTRACT_DRY_RUN=1`) runs the
  same small NegEx/ConText-shaped rule-based matcher as before (trigger word
  + local text window, `literature/14` R-IE-01/R-IE-02 design shape) —
  unchanged logic, now reached only by explicit request, with zero network
  calls guaranteed (`tests/test_extract.py::
  TestDryRunRunsWithoutApiKeyOrNetworkCalls::test_dry_run_never_calls_
  complete_fn` injects a complete_fn that raises if ever reached, and
  asserts it never is).
- `Extractor()`'s default (`dry_run=False`) always attempts a real
  `llm.complete()` call. If no OpenAI/Google key resolves anywhere `llm.py`
  looks (env, then `.env`, canonical name before alias — see `llm.py`'s own
  docstring), `llm.complete()` raises `llm.MissingAPIKeyError` — a typed
  error naming exactly which env vars / `.env` keys were checked and how to
  fix it — and `extract.py` lets it propagate unwrapped rather than catching
  it and quietly degrading (`tests/test_extract.py::
  TestMissingApiKeyRaisesRatherThanSilentlyFallingBack`, including one test
  that exercises the real seam end-to-end with every key source blanked
  out, not just a mock of the failure).

Every real `llm.complete()` response's `cost_usd` / `prompt_tokens` /
`completion_tokens` accumulate onto `Extractor.total_cost_usd` /
`total_prompt_tokens` / `total_completion_tokens` (0 for cache hits and
always 0 under `dry_run`), so a caller — the still-outstanding bulk-
extraction script — can report real spend per admission or per patient
without reading `llm.get_ledger()` itself.

**Known consequence, flagged rather than silently absorbed:** two scripts
outside this story's file list still call the old constructor shape —
`scripts/generate_extract_eyeball.py` passes `force_fallback=True` (now a
`TypeError`, a hard crash, since that kwarg no longer exists) and
`scripts/generate_resolve_eyeball.py` calls bare `Extractor()` (previously
silent-free rule-based; now, since this sandbox's `.env` **does** carry real
`OPEN_AI_KEY`/`GOOGLE_API_KEY` values, it would attempt a real, billed
`llm.complete()` call instead of erroring or silently falling back). Neither
script was in this story's Files-to-touch list and neither was modified
here; both need a one-line `dry_run=True` fix (or a deliberate real run) in
a follow-up before either is invoked again.

The eyeball artifact (`samples/extract-eyeball-10056223.md`) was generated
by the rule-based path (pre-rewire, before a key was ever configured in this
sandbox) and says so at the top in bold. It documents, with real corpus
quotes, two genuine mistakes the fallback makes — a false-positive
family-history skip (a `"fever"` mention gets dropped as
not-associated-with-patient purely because "sister" appears earlier in the
same sentence, even though the sentence is about the patient) and a
scope-bleed false negation (a negation trigger meant for "no blood or
diarrhea" bleeds backward onto an unrelated medication mention in the same
sentence). Both are documented, real, and un-hidden — see the eyeball's own
"Honest read on quality" section — because they are exactly the class of
error `literature/14`'s Part 3 predicts for window-based rule systems with
no real clause-boundary or coreference awareness, and exactly the class of
error decisions/002 and this story both name as highest-risk. The
recommendation recorded there is explicit: re-run the same admission through
the LLM path (`Extractor()`, default, now that a key is actually wired) and
specifically re-check those two failure classes rather than assuming the
LLM path fixes them for free — `literature/14` R-IE-28 is clear that even a
capable zero-shot model is *specifically* weaker on exactly this kind of
scoping nuance, not just "generally better." Regenerating that eyeball
against the real corpus is explicitly **not** done by this story ("Do NOT
run a bulk extraction — that is the next phase's job").

## 7. Subject/object role-reversal repair — a silent-corruption bug worse than a drop

**2026-08-17.** An adversarial verification pass re-ran real LLM extraction
(`gemini-3.5-flash-lite`, via the `llm.py` seam) across three real patients
and checked the *emitted facts themselves*, not just the drop log — and
found a defect the drop-log view structurally could not surface, because
the corrupted facts pass `contracts.validate()` and count as `emitted`.
Measured on real output: **22.2%–46.4%** of `TAKES_MEDICATION` facts across
the three patients carried a corrupted `object.name`.

### 7.1 The defect

The system prompt's own subject/object convention (§ above) is: `subject`
is normally the PATIENT, `object` is the real clinical entity. On some
candidates the model returns the roles **reversed** relative to its own
stated convention — `subject_name=<drug>, object_name="patient"` instead of
`subject_name="patient", object_name=<drug>`. Pre-fix, `_handle_candidate`
hardcoded `subject = patient_id` for every non-`CURRENT_DOSAGE_OF` predicate
(correctly — the patient really is the subject) and then **blindly trusted
`object_name`** for the entity name. On a reversed candidate this discards
the drug name entirely and writes the literal string `"patient"` into
`object.name` — a fact that reads "the patient takes medication *patient*."

This is a materially worse failure than a dropped fact. A drop is visibly
absent — `dropped_no_predicate` / `dropped_by_rule` are already first-class,
zero-filled, always-reported numbers (§6's own PRN-fix precedent). A
role-reversed fact is **present, individually well-formed, and wrong**: it
passes every existing `validate()` check (closed predicate, binary
polarity, non-empty `turn_ids`, non-negative `canonical_id`s — nothing in
the pre-fix contract said anything about what `object.name` should actually
*contain*), gets counted in `decision_counts()['emitted']`, and silently
guts the medication list while every counter reports success. Real evidence
in `samples/extract-eyeball-10056223.md`: row 54 (`TAKES_MEDICATION | 10056223
→ patient`, admission `23103238`, turn 13 — "We'll give you Tessalon Pearls
to help with the cough") and rows 86–88 (same corruption, admission
`25778194`, turn 40 — "...Prochlorperazine for nausea if it comes back, and
oxycodone for pain as needed"). Both quotes are the exact ones the PRN
regression fix (§ above, `_PRN_BUGFIX_PAYLOAD`) was built to keep from
dropping — but here the model didn't drop them via the wrong i2b2 tag, it
emitted them with the wrong entity name instead, a completely different
failure mode of the same underlying quotes. And the model is
**inconsistent, not uniformly wrong**: the same eyeball's rows 62–66 show
`prochlorperazine`-adjacent medications correctly attributed at three other
admissions for this same patient — which is exactly why this went unnoticed
by any prior spot-check that only sampled a few rows.

### 7.2 The fix — two layers, deliberately not either/or

A single-layer fix (prompt-only, or repair-only) leaves a gap: a prompt
change reduces the *rate* the model makes this mistake but cannot guarantee
zero, and a repair-only fix treats the symptom forever without ever
narrowing how often it needs to fire. Both layers ship together:

**Layer 1 — repair at ingest (defensive, `_handle_candidate`).** Once
`predicate` is known (right after canonicalization, before any
time-resolution work is wasted on a candidate that might get dropped), a
new check runs for every predicate **except** `CURRENT_DOSAGE_OF` — which
is excluded on purpose, because its `object` is a dose value ("60mg"),
never patient-referring in the first place, so the same test there would be
a category error, not a reversal check (§5 above documents why
`CURRENT_DOSAGE_OF` has genuinely different role semantics):

```
is_patient_ish_token(object_name)              -- object says "patient"?
    and not is_patient_ish_token(subject_name)  -- but subject holds real content?
    -> REVERSED: swap subject_name's value into the object position
       (repaired_role_reversal = True on the side-log entry)

is_patient_ish_token(object_name)
    and (is_patient_ish_token(subject_name) or subject_name is blank)
    -> UNREPAIRABLE: no real entity name survives on either side
       -> drop, decision = "dropped_role_reversal_unrepairable"
       (a NEW, visible drop category, not a silent skip)

otherwise -> untouched, normal path
```

`is_patient_ish_token` (`contracts.py`, shared with the layer-3 guard below
— one definition, not a duplicated regex) matches a small closed set of
generic patient-referring placeholders — the literal words `"patient"` /
`"the patient"` / `"pt"`, the personal pronouns `he/she/him/her/himself/
herself/i/me/myself/you/yourself`, and (when a `patient_id` is supplied)
the patient's own id string — against the name after stripping surrounding
punctuation and lower-casing it. This is deliberately a **closed set of
placeholders**, not a heuristic over drug-name shape: it says nothing about
what a real entity name looks like, only what a *non*-entity, patient-
referring stand-in looks like, so it cannot accidentally reject a real (if
unusual) medication or condition name. This is implemented **generally**,
not as a `TAKES_MEDICATION` special case — the story's own real-corpus
evidence (§7.1) shows the same corruption on medication candidates from
multiple admissions of the same patient, and decisions/002's own
diagnosis-vs-symptom failure modes give no reason to expect `HAS_CONDITION`
/ `HAD_PROCEDURE` candidates are immune to the same subject/object mix-up.

**Layer 2 — prevent at the source (schema + prompt, `_CANDIDATE_FACT_SCHEMA`
/ `_SYSTEM_PROMPT`).** The wire schema's field *names* (`subject_name`,
`object_name`) are left alone — renaming them to clinical-role-specific
names (e.g. `patient_or_medication_name` / `clinical_entity_name`) was
considered per the story's own suggestion, but rejected: every existing
test fixture in `tests/test_extract.py`'s `_candidate()` helper builds dicts
keyed on the current names, and a rename would silently zero out every
field via `raw.get(...)` defaults across the entire existing suite rather
than failing loudly — a much worse failure mode than the one being fixed,
and out of this fix's remit to coordinate (test authorship here belongs to
`test-lead`/`test-unit`, not this story). Instead, both the JSON-Schema
`description` strings and the system prompt's own "Subject/object
convention" paragraph were tightened: `object_name`'s description now
spells out, explicitly, that it must never be a patient-referring word and
names the failure mode by name ("If you find yourself about to write a
patient-referring word here, you have the subject/object roles backwards");
the prompt adds one worked CORRECT/WRONG pair contrasting the right
orientation for a medication against the exact reversed shape this bug
produces — the same worked-example discipline §1 above already uses for
the i2b2 tags (contrast, not just a rule statement, is what the existing
PRN prompt fix (§ above / `decisions/` PRN story) found actually moves
model behaviour).

**Layer 3 — guard the contract (`contracts.validate()`).** A last-line,
predicate-shape-based check: for every predicate except
`CURRENT_DOSAGE_OF`, `object.name` must never be `is_patient_ish_token`.
Because `_handle_candidate` already always sets `subject.name = patient_id`
for this predicate family, `fact.subject.name` doubles as the patient_id to
compare `object.name` against — no separate parameter threading needed.
This is deliberately independent of layer 1: even if a future call site
constructs a `ClinicalFact` without going through `_handle_candidate`'s
repair logic (a different script, a different pipeline stage, a bug in the
repair logic itself), a fact shaped like this can never reach `emitted`
silently again — `validate()` is the one gate every `ClinicalFact` this
codebase constructs is meant to pass before being counted as valid
(`ARCHITECTURE.md` §4).

### 7.3 Countability — a silent repair is only marginally better than a silent corruption

Layer 1's repair *branch* is itself logged with the same discipline §6
above applies to the dry_run/key-presence fix: **the repair rate must be a
first-class, always-visible number, not just a code path that happens to
run.** `AssertionLogEntry.repaired_role_reversal` (`False` by default,
mirroring the existing `.prn` field's own pattern) is set on the emitted
entry whenever the swap fired; `Extractor.decision_counts()` now also
returns a `repaired_role_reversal` key — deliberately **not** a `decision`
partition member (it is a non-exclusive counter: a repaired candidate is
still counted once under `emitted`, and once again under
`repaired_role_reversal`, so `sum(decision_counts().values()) ==
len(assertion_log)` no longer holds once any repair has fired — documented
in the method's own docstring so this isn't mistaken for a bug later). The
unrepairable branch gets its own `_KNOWN_DECISIONS` member,
`dropped_role_reversal_unrepairable`, zero-filled exactly like
`dropped_no_predicate` was in §6's own fix, for the same reason: a
currently-zero count for a real failure mode must still be structurally
present in the stats, not merely absent from a table. Both numbers flow
into `scripts/generate_extract_eyeball.py`'s existing decision-counts
summary line automatically (it iterates `sorted(decision_counts())`
generically) — no separate change to that script was needed or made by
this fix.

### 7.4 What this fix deliberately does not attempt

Layer 2 (prompt/schema tightening) is expected to *reduce* the reversal
rate, not eliminate it — this fix does not claim, and does not re-run real
inference to measure, a specific post-fix reversal rate (that
measurement — re-running the same three patients' real extraction and
re-checking the corrected `TAKES_MEDICATION` object names — is the natural
next verification step, explicitly out of this story's scope, mirroring §6's

fix does guarantee, structurally, regardless of how often the model still
reverses roles: no reversed candidate can reach `emitted` with a corrupted
`object.name` ever again — it is either repaired (countable) or dropped
into a visible category (countable), never silently wrong.
